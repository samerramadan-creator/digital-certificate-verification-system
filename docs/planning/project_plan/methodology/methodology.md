# Project Methodology


> **Iterative / RAD**
>
> We will build the Digital Certificate Verification System in versions, and we will use prototypes of the screens so the staff can give feedback early.

## Why we chose it

- **Step by step:** the requirements are clear (five business requirements in the System Request) and the system has clear parts: the public verification page, the admin dashboard and the old certificate records. We build them as versions, one after the other.
- **Fast first version:** version 1 lets employers verify a certificate in seconds, so the faculty gets value early.
- **User feedback:** Student Affairs staff may resist changing their routine, so they see prototypes of the verification page and the admin dashboard early and tell us what to fix before we build everything.
- **Safe:** graduate data must be protected, so we test each version before we add the next one.

## Why we did not choose the others

| Methodology | Why we did not choose it |
|---|---|
| **Waterfall** | The requirements are clear, but the staff would see the system only at the end. A mistake in the design or the security would be found late, and changes after a phase ends are difficult. |
| **Parallel** | It needs many teams working at the same time. Our team has only four students and the system is small, so the extra work of joining the parts is not worth it. |
| **Agile** | It is very flexible, but it needs users who are available all the time and requirements that change often. Here the requirements are mostly fixed in the System Request, and the staff have limited time. |
